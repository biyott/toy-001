# 상한 부하 렌더링 읽기 진단

담당: architecture / 렌더링. 요청 모델·강도 Astra xhigh, 실제 런타임 메타 독립 확인은 미확인.

이 문서는 기존 측정 파일과 소스의 읽기 결과다. **렌더링 코드, 테스트, 빌드, 브라우저, 벤치마크는 변경하거나 실행하지 않았다.** 아래 원인과 개선 효과는 A/B 검증 전의 가설이다.

## 결론

첫 수정 후보는 **적 공격 영역의 정적 채움·해칭을 작은 경계에 맞춘 이미지로 한 번만 만들고 재사용**하는 것이다. 현재 최대 84개 영역에 매 프레임 `clip('evenodd')`와 긴 해칭 선 묶음을 다시 그리는 구조가 우선 의심된다. 실제 위치, 공격 모양, 시간에 따른 깜박임, 예고 화살표, 상단 위험 경계는 그대로 유지할 수 있다.

두 번째는 별도 A/B 후보로 **고정 화면 비네트 이미지를 resize 때만 생성하고 불필요한 투명 clear를 제거**하는 것이다. 첫 후보보다 기대 효과는 낮고, 단독 개선 폭을 확인한 다음 유지 여부를 결정해야 한다. 둘 모두 기능·개체 수·판정·DPR·시각 콘텐츠를 줄이지 않는다.

## 직접 확인한 측정

출처: `evidence/final-performance.json`. Chrome 151.0.7922.169, Headless Chrome, WSL2 Linux, i7-14700KF, 노출된 논리 CPU 8, 메모리 약 23.47GiB. 소프트웨어 래스터 환경이라는 설명은 메인 보고 기반이며 JSON 자체는 그래픽 백엔드를 직접 식별하지 않는다.

| 항목 | 1280×720, DPR 1 | 1920×1080, DPR 1 |
|---|---:|---:|
| 측정 시간 | 60초 | 60초 |
| 평균 FPS | 26.968 | 16.301 |
| 평균 frame time | 37.081ms | 61.347ms |
| p95 frame time | 50ms | 83.3ms |
| renderer JS 평균 | 3.124ms | 3.273ms |
| 전체 측정 JS 평균 | 4.496ms | 5.460ms |
| engine JS 평균 | 1.262ms | 2.043ms |
| 1픽셀 readback 동기화 평균 | 32.518ms | 55.900ms |
| 실제 적/투사체/픽업 | 180 / 300 / 260 | 180 / 300 / 260 |
| 실제 공격 영역 | 20~84 | 18~84 |

- 투사체는 플레이어 220 + 적 80이다. 적 투사체를 플레이어 주변으로 매 프레임 되돌려 비행/충돌 부하를 유지한다. 일반 플레이를 나타내는 배치가 아니다.
- 표의 목표 영역 10개는 fixture가 유지하는 기본 영역이다. 적 FSM과 무기가 만든 추가 영역까지 포함하면 실제로 84개다. 결과를 “영역 10개에서 27fps”라고 보고하면 부정확하다.
- 1080p의 픽셀 수는 720p의 2.25배다. renderer JS는 약 4.8% 증가하지만 평균 frame time은 약 65% 증가한다. 자바스크립트 자료구조 최적화보다 래스터·알파 합성·화면 픽셀 비용을 먼저 살펴볼 근거다. 개별 기능이 원인임을 증명한 것은 아니다.
- readback은 5초마다 한 번, 총 11회이며 명령 큐·드라이버·합성 대기를 포함한다. 이를 “순수 GPU 55.9ms” 또는 “순수 Canvas 채우기 55.9ms”로 단정하면 안 된다.
- 720p는 1,618프레임 중 1,549개가 33ms를 넘었다. 11회 readback만으로 전체의 지속적인 저하를 설명할 수 없다.
- 정상 600초 승리, 최대 적 33, 마지막 3,600프레임 평균 약 60fps/p95 16.7ms 및 1080 demo 약 55.34fps/p95 33.3ms는 메인 보고 기반이다. 이 합성 상한 측정과 별도 검증 항목으로 유지한다.

## 소스에서 확인한 비용

### 1순위: 공격 영역의 반복 clip + 해칭

위치: `src/render/renderer.ts:41`의 `drawZone`, 특히 51~57행; 호출은 300행의 바닥 패스와 346행의 위쪽 경계 패스.

- 각 적 영역의 바닥 패스가 `zonePath → fill → clip('evenodd') → 많은 대각선 stroke → restore → zonePath → stroke`를 반복한다.
- 해칭 범위 `r = max(radius,length)+30`; x는 `-2r..2r`, 17 간격이고 선마다 y 범위는 `-r..r`이다.
- 길이 390인 골렘 직선은 r=420이라 약 99개의 선을 준비한다. 각 선의 y span은 840이고 실제 길이는 약 939다. 실제 공격 직선 폭은 60뿐이다. 일반 조준 선은 폭 16~20으로 더 좁다.
- 상한에서 이 같은 선·클립이 다수 겹친다. 픽셀은 최종 클립 영역만 바뀌더라도 경로 처리와 안티앨리어스 클립 비용이 반복된다. 실측 프로파일 없이 정확한 시간 비중은 알 수 없다.
- 위쪽 패스는 해칭을 다시 그리지 않고 경계만 그린다. 따라서 “전체 해칭을 두 번 그린다”는 진단은 틀리다. 가림보다 위에서 위험 경계를 읽게 하는 목적이 있어 상단 경계 제거는 권하지 않는다.

### 반복 픽셀 채움: 중복 지우기와 비네트

위치: `renderer.ts:284~287`, `359~363`, context 생성 224행.

- 프레임마다 전체 화면 `clearRect`, 같은 범위의 불투명 바닥색 `fillRect`, 불투명 ground chunk blit가 이어진다. 투명 clear는 뒤의 불투명 fill이 모두 덮으므로 시각적으로 불필요하다.
- 전체 화면 방사형 비네트를 매 프레임 새로 만들고 반투명으로 합성한다. 이 비네트는 화면 크기 외에는 달라지지 않는다.
- title의 선형 veil은 플레이 상한 측정에서 실행되지 않는다. 이를 플레이 병목으로 지목하지 않는다.
- renderer/모든 효과에 Canvas `shadowBlur`나 `filter: blur()`는 없다. 그림자는 단순 타원 두 개다. 따라서 존재하지 않는 실시간 블러를 제거한다는 제안은 하지 않는다.

### 그 외 비용은 확인했지만 이번 우선 수정에서 제외

- 액터는 128×144 논리 캔버스, 실제 소스 256×288이며 보통 scale 0.53~0.68로 보인다. 도형·외곽선은 최초 한 번만 생성하고 이후 이미지 한 번으로 그린다. 외곽선 8방향 합성을 매 프레임 한다는 해석은 틀리다.
- 액터·소품의 투명 여백을 잘라 blit 영역을 줄일 여지는 있다. 다만 이미 캐시된 그림이고 이번 해상도 비용과 영역 클립보다 우선할 증거는 약하다. 큰 아트 변경이나 이미지 해상도 하향은 제안하지 않는다.
- 지면의 풀 패치와 길은 chunk가 처음 만들어질 때만 생성된다. fixture는 입력이 없고 카메라가 거의 고정이므로 큰 풀 패치 루프를 60초 내내 실행한다고 볼 수 없다.
- 지면은 캐시돼도 프레임당 전체 화면에 가까운 이미지 픽셀을 덮는다. 이는 카메라/월드 배경을 표시하는 필요한 작업이며 지금은 배경 레이어 재설계까지 확대하지 않는다.
- 300개 투사체와 260개 픽업은 아직 벡터로 그린다. 특히 정령과 적 포자의 작은 반투명 도형 수가 많다. 다만 새로 구현한 비행 실루엣·표현을 줄이기보다 먼저 정적 위험 영역을 재사용하는 것이 품질 위험이 낮다.
- 파티클은 450, 피해 숫자는 48로 제한된다. 큰 별/숫자 제거 또는 적 수 축소로 상한 측정을 통과시키지 않는다.

## 제안 A: 적 영역의 정적 레이어를 tight-bounds 캐시에 저장

이것을 첫 단독 변경으로 권고한다. 범위는 `src/render/renderer.ts`와 필요하면 렌더 전용 작은 캐시 파일 하나다.

1. 도형을 원점·회전 0의 로컬 좌표로 만든다. 원/고리는 `2r` 크기, 직선은 `length × width`, 부채꼴은 실제 arc bounds + stroke padding으로 경계를 계산한다. 직선에 `2length × 2length` 캔버스를 만들지 않는다.
2. 키는 `shape,radius,innerRadius,length,width,staticStyle,qualityScale`이다. `zone.id`, x/y, angle, telegraph 값, game time을 키에 넣지 않는다. 동일 규격의 새 공격들이 캐시를 공유해야 한다.
3. 정적 레이어는 **채움 마스크/색 레이어와 해칭 레이어**로 분리한다. 채움에는 현재 프레임의 `.10~.16` 예고 pulse 또는 활성 `.27` alpha를 적용하고, 해칭에는 현재와 같은 고정 alpha를 적용한다. 시간 정보를 그림에 굳히지 않는다.
4. world 위치로 translate하고 실제 angle로 rotate하여 이미지들을 그린다. 원/고리는 회전이 불필요하다. 위치와 판정의 기준 데이터는 계속 `state.zones`다.
5. 실제 예고/활성 여부에 따른 선 두께, 점선 경계, 가운데 경고표식, 방향 화살표, 왕 포자의 무해한 목표 표식, 상단 가림 방지 경계는 현재 코드의 동적 표시를 유지한다. 공격 시작과 끝을 캐시 수명으로 판단하지 않는다.
6. 캐시는 LRU 약 32개 및 총 픽셀 상한(예: 두 레이어 합계 8M pixels, RGBA 약 32MiB) 중 먼저 도달하는 기준으로 제한한다. 비정상적으로 큰 영역은 원래 경로로 fallback한다. resize의 품질 배율 변경 및 renderer.dispose에서 비운다.
7. 연속 실수 radius가 있어 캐시가 새로 생기는 경우를 검사한다. 값 반올림으로 실제 공격 모양을 바꾸지 않는다. 엔진의 소수 규격 그대로 키를 만들고 LRU로 제한한다.

예상 원리: 수십 개의 clip/긴 stroke 묶음을, 첫 생성 후 1~2개의 작은 이미지 blit로 교체한다. 특히 긴 직선의 래스터 바운딩 영역을 작게 유지한다. **FPS 개선량이나 60fps 도달은 아직 알 수 없다.** 이미지 알파 합성·영역 겹침 자체는 남는다.

더 작은 대안은 17×34 또는 2배 해상도의 반복 해칭 텍스처를 `CanvasPattern`으로 한 번 만들고 현재 도형에 `fill('evenodd')` 하는 것이다. 이는 clip과 긴 선 묶음만 제거하므로 구현 위험·메모리가 더 작다. 메인이 전체 영역 캐시의 일정/리스크를 높게 판단하면 이 대안을 A의 첫 버전으로 선택할 수 있다. 둘을 중복 적용할 필요는 없다.

검증:

- 같은 state와 같은 time으로 패치 전후의 circle/ring/line/cone, telegraph>0/active, 회전된 직선, 가려진 위험 경계, royal-spore-target를 캡처해 비교한다.
- 긴 선은 실제 길이/폭/방향을 유지하고, 왕 착탄 표식이 먼저 피해 폭발처럼 변하지 않는지 확인한다.
- pause/levelup에서 pulse와 위치가 멈추는지 확인한다.
- 첫 생성 후 반복 zone 84개에서 캐시 크기·픽셀 수가 증가하지 않고, 새 ID/위치/angle이 캐시 miss를 만들지 않는지 확인한다. resize 후 선명도와 잘림을 확인한다.
- 기존 동일 60초 fixture를 720p/1080p에서 순차 재실행한다. seed, DPR, 개체 수, HUD, readback 주기를 유지한다. 평균/p95 frame, JS, readback과 실제 zone 범위를 기존 결과 옆에 기록한다. 이전 baseline을 덮지 않는다.

## 제안 B: 고정 화면 비네트와 불필요한 clear 정리

A를 검증한 후 두 번째 독립 A/B 변경으로만 권고한다.

- context는 프레임 전체를 불투명하게 덮는 용도이므로 `getContext('2d', {alpha:false})`를 검토하고, 매 프레임의 `clearRect`를 제거한다. 바닥 `fillRect`는 남겨 카메라 흔들림/경계에서도 완전한 덮기를 보장한다.
- 현재 방사형 비네트는 `resize` 때 정확한 backing 크기와 같은 색으로 투명 offscreen 이미지에 한 번만 그린다. 매 프레임에는 동일 위치에 이미지 한 번을 합성한다. 새 색상, 흐림, 해상도 저하를 넣지 않는다.
- title veil도 같은 방식으로 준비할 수 있지만, 플레이 성능 개선으로 계산하지 않는다.
- 예상 원리: 전체 화면 중복 clear와 반복 gradient 계산/래스터 작업을 줄인다. 마지막 반투명 이미지 합성 비용은 남으므로 큰 개선을 약속하지 않는다.
- 리스크: headless 그래픽 경로에서 이미지 샘플링이 gradient shader보다 반드시 빠르다고 보장할 수 없다. A/B에서 이득이 없거나 선명도가 달라지면 비네트 캐시 부분은 되돌리고 clear 제거만 유지한다.
- 검증: 두 해상도 title/play/pause 캡처의 전체 톤·가장자리·투명도 동등성, 화면 resize/대시 흔들림에서 미도색 픽셀 없음, 같은 60초 fixture 결과를 별도 기록한다.

## 의사결정과 남은 확인

권고 순서는 A 단독 → 재측정 → 필요할 때 B 단독 비교다. 문제의 실제 시간 비중을 알기 전에 해칭, 투사체, 아트 해상도, DPR, UI를 한꺼번에 바꾸지 않는다. 정상 실플레이 기록은 유지하고, 상한 부하 성능 미달도 별도 사실로 남긴다.
