# A01 — 렌더링·아트·게임 구조 제안

- 작성 범위: 요구사항 검토와 설계만. 게임 구현·브라우저 검증은 아직 하지 않았다.
- 작성자 역할: researcher / 아트·렌더링·공용 구조.
- 요청 모델/강도: `gpt-6-astra` / `xhigh`. 실제 런타임 모델·강도는 이 에이전트가 독립적으로 확인할 수 없어 **미확인**.
- 원문: 사용자 첨부 `붙여넣은 텍스트.txt`를 읽었다. 최초 저장소는 `.codex/config.toml`만 확인되었고, 읽기 가능한 `/AGENTS.md`, 상위 및 프로젝트 `AGENTS.md`는 없었다.
- 최신 시간 제한: 메인 전달에 따라 시작 2026-09-19T11:42:37Z, 마감 **2026-09-19T14:42:37Z**. 정상 한 판 10분 요구는 유지한다.
- 상태: 메인이 채택·조정할 설계 초안. 현재 아트 품질이나 60fps 달성을 주장하지 않는다.

## 1. 단일 추천

**TypeScript + Vite, Canvas2D 절차적 카툰 디오라마, 일반 DOM 한국어 UI**를 사용한다. 외부 게임 엔진·3D 모델·텍스처 없이 형태, 팔레트, 명암, 애니메이션을 직접 통제한다. 3시간 제한에서 실체가 있는 귀여운 캐릭터와 2.5D 공간을 확보하면서 전투·성장·보스·검증에 시간을 남길 수 있다.

실제 Three.js 3D는 광원과 가림을 자동 해결하지만 모델링, 리깅, 그림자 조정, 카메라 충돌 및 아트 일관성 비용이 지금의 핵심 위험이다. Canvas2D를 고른다고 평평한 기호 게임을 만들면 안 된다. **머리·몸·손·발, 보이는 윗면·옆면, 접지 그림자, 높이 차이, 발점 정렬, 가림**을 첫 장면의 필수 합격 기준으로 삼는다.

첫 장면을 실제 1280×720 화면으로 캡처하여 한 차례 검토한 후 선택을 확정한다. 부족하면 우선 비율·색·레이어를 고친다. 특별한 실행 장애가 없으면 이후 엔진을 바꾸지 않는다.

## 2. 화면과 아트 규칙

### 좌표와 조작

- 플레이 평면은 화면 방향과 같은 `x`(오른쪽), `y`(아래쪽) 좌표다. `screenX = centerX + (x-camera.x)*zoom`, `screenY = centerY + (y-camera.y-height)*zoom`.
- `height`는 점프·대시·표현을 위한 시각 높이이며, 충돌 위치는 항상 발점 `(x,y)`다. 카메라 각도를 만들려고 입력 벡터를 45도 회전시키지 않는다.
- 위 입력은 화면 위로, 오른쪽 입력은 화면 오른쪽으로 이동한다. 대각선 입력은 정규화한다. 키보드·게임패드·터치는 같은 입력 벡터를 사용한다.
- 엄밀한 등각 좌표 대신 **윗면이 보이는 고정 쿼터뷰 카툰**을 사용한다. 지면 도형과 소품 윗면을 세로 0.55~0.65 비율로 표현하여 깊이를 만든다. 렌더링 때문에 전투 좌표계가 왜곡되지 않는다.
- 기준 화면 1280×720. `zoom = clamp(min(width/1280,height/720),0.7,1.5)`를 시작점으로 삼고 실제 두 해상도에서 확인한다. 캔버스 좌표는 CSS 픽셀이며 backing store만 DPR을 반영한다.

### 실루엣과 팔레트

- 작은 기사: 발점에서 머리 끝까지 약 48~56px, 머리 23~27px, 몸 18px 전후. 약 2.2등신. 투구의 눈 틈, 볼, 둥근 손과 짧은 장화가 보인다.
- 일반 적: 30~52px. 슬라임은 둥근 젤리, 버섯은 넓은 갓, 고블린은 큰 귀, 해골은 투구·방패, 박쥐는 가로 날개, 정령은 마법봉으로 작은 크기에서도 구분한다.
- 보스: 100~145px. 머리/갓/몸집에 면적을 주고 같은 외곽선·그림자 규칙을 유지한다.
- 바닥 `#8EA987`, 밝은 풀 `#B9CE95`, 크림 `#FFF0CD`, 양피지 `#F5DEB5`, 나무 `#85644C`, 외곽선 `#493F45`, 하늘색 `#9ACFDE`, 마법 보라 `#A881D5`, 금색 `#F2C15B`.
- 위험은 살구·주홍 + 해칭/삼각표시/수축하는 경계로 표시한다. 경험치의 청록과 위험을 분리한다. 색만으로 공격 종류를 설명하지 않는다.
- 광원은 좌상단. 재질당 기본색·밝은 면·어두운 면의 3단계. 부드러운 그림자는 발밑 타원이고 긴 방향성 그림자는 우하단이다. 외곽선은 1.5~2.5px로 통일한다.

### 디오라마 공간

- 전투장은 넓은 풀밭, 굽은 돌길, 마법 우물/룬석을 중심으로 구성한다. 이끼 낀 작은 성문과 분절한 성벽, 목조 지붕, 깃발, 나무 군집이 바깥쪽에 프레임을 만든다.
- 중앙 장식은 꽃·돌·버섯처럼 낮고 이동 가능한 것으로 둔다. 실제 충돌 장애물은 돌/우물/성벽처럼 크기와 받침이 분명한 소수만 사용한다.
- 모서리와 장식 밀집 구역에 적을 밀어 넣는 구조를 피한다. `Prop.solid`를 명시하고 시각 장식과 충돌 데이터를 분리한다.
- 월드가 플레이어를 따라 움직여도 배경이 끝없는 랜덤 점처럼 보이지 않도록 랜드마크를 반복 배치하지 않는다. 원점 주변 성문·우물·돌길을 고정 시드로 만든다.

### 정렬과 가림

1. 지면·돌길·꽃.
2. 모든 접지 그림자.
3. 바닥 공격 예고와 지속 영역.
4. 캐릭터·적·높은 소품을 `footY`, 동률이면 안정적인 ID 순서로 정렬.
5. 발사체·타격·텍스트.
6. 가려진 플레이어 윤곽과 위험 영역의 얇은 경계.

- 긴 성벽은 작은 구간으로 나누어 각각 발점을 가진다. 큰 하나의 이미지로 정렬하면 벽 옆을 지나는 캐릭터가 잘못 가려진다.
- 나무/건물의 화면 경계에 플레이어가 겹치고 플레이어 발점이 뒤에 있을 때 해당 소품을 약 0.35~0.5 투명도로 낮춘다. 필요하면 마지막에 플레이어의 밝은 외곽선만 추가한다.
- 적보다 예고 영역을 읽기 쉽게 유지한다. 높은 장식은 위험 구역을 가리지 않도록 투명도 판정에 포함한다.

## 3. 타격감과 애니메이션

- 이동: 보행 위상에 따라 몸을 2~3px 들고, 좌우 손발과 기울기를 반대로 움직인다. 정지하면 제자리 호흡만 남는다. 이동 방향을 따라 눈·무기 방향을 바꾼다.
- 공격: 준비 60~90ms → 타격 70~120ms → 회복 100ms 전후. 자동 공격도 준비/타격/회복을 구분한다. 물리 피해 판정은 준비가 끝나는 한 시점에서만 발생한다.
- 피격: 적 80ms 밝은 색, 타격 방향으로 짧은 밀림, 별 조각 3~6개, 피해 숫자. 플레이어는 다른 음과 윤곽 반응으로 구분한다.
- 대시: 짧은 무적 구간과 속도 상승, 잔상 3개, 쿨다운 HUD. 대시 입력은 눌림 이벤트만 소비하여 키를 누르고 있을 때 연속 발동하지 않는다.
- 화면 흔들림은 일반 타격에서 거의 없고 강한 피격·보스 충격만 1~4px로 제한한다. 설정을 줄이면 실제 카메라 흔들림을 0~20%로 낮춘다.
- 전체 화면 흰색 번쩍임은 사용하지 않는다. 레벨업은 작은 금색 링과 밝은 별, 부드러운 음으로 표현한다.
- 효과 시간은 게임 시간 기준이므로 일시정지·레벨업 선택 중 전투 이펙트와 위험 예고도 멈춘다.

## 4. 공용 API 초안

메인이 타입 이름과 필드를 먼저 확정하여 `CONTRACTS.md` 및 공용 타입에 기록한다. 아래 계약은 파일 병렬 작업의 경계를 위한 초안이다.

```ts
type Vec2 = { x: number; y: number };
type GameMode = 'normal' | 'demo' | 'challenge';
type CharacterId = 'knight' | 'mage' | 'ranger';
type Phase = 'title' | 'playing' | 'paused' | 'levelup' | 'victory' | 'defeat';
type WeaponId = 'sword' | 'bow' | 'wisp' | 'fireball' | 'frost' | 'lightning';

interface RunConfig {
  mode: GameMode;
  seed: number;
  character: CharacterId;
}
interface InputFrame {
  moveX: number; // normalized screen-aligned vector
  moveY: number;
  dashPressed: boolean; // one-shot edge
  pausePressed: boolean;
}
interface Body {
  id: number;
  x: number;
  y: number;
  prevX: number;
  prevY: number;
  radius: number;
  facing: number; // radians in the same x/y plane
}
interface GameState {
  phase: Phase;
  mode: GameMode;
  seed: number;
  elapsed: number; // seconds; only advances in playing
  duration: number; // normal 600, demo 180
  player: Player;
  enemies: Enemy[];
  projectiles: Projectile[];
  pickups: Pickup[];
  zones: Zone[];
  props: Prop[];
  weapons: WeaponState[];
  upgradeChoices: UpgradeChoice[];
  stats: RunStats;
}
type GameCommand =
  | { type: 'start'; config: RunConfig }
  | { type: 'pause' }
  | { type: 'resume' }
  | { type: 'selectUpgrade'; choiceId: string }
  | { type: 'restart' }
  | { type: 'returnTitle' };

interface Game {
  getState(): Readonly<GameState>;
  step(dt: number, input: InputFrame): void;
  dispatch(command: GameCommand): void;
  drainEvents(): GameEvent[]; // queue emptied; each event consumed once
}
interface GameRenderer {
  resize(width: number, height: number, dpr: number): void;
  consumeEvents(events: readonly GameEvent[]): void;
  render(state: Readonly<GameState>, alpha: number, settings: Settings): void;
  dispose(): void;
}
interface GameUI {
  render(state: Readonly<GameState>, profile: SaveData): void;
  dispose(): void;
}
```

- `Player/Enemy/Projectile/Pickup/Zone/Prop/WeaponState/UpgradeChoice/RunStats` 필드는 전투 담당이 제안하고 메인이 단일 공용 타입에서 확정한다. 여러 담당자가 각자 같은 타입을 정의하지 않는다.
- `Enemy`는 행동/애니메이션 상태 `kind, hp, maxHp, state, stateTime, hitFlash`를 가진다. 렌더러가 HP로 보스 단계를 추측하거나 피해를 계산하지 않는다.
- `Zone`은 `shape:'circle'|'ring'|'line'|'cone'`, 발점, 방향, 크기, `telegraphRemaining`, `activeRemaining`, 팀을 명시한다. 예고와 실제 피해가 같은 기하 데이터를 사용해야 한다.
- `Projectile`은 `owner, weaponId, vx, vy, damage, lifetime, pierceRemaining, generation, hitIds`를 가진다. 이미 맞은 적에 매 프레임 중복 피해를 주지 않는다.
- `GameEvent` 종류는 최소 `attack/hit/kill/pickup/levelup/dash/bossSpawn/victory/defeat`. 좌표·sourceId·weaponId·피해량·강도 등 필요한 정보만 전달한다.
- root가 `drainEvents()`를 한 번 호출한 뒤 같은 배열을 renderer와 audio에 전달한다. 두 소비자가 각각 drain하면 뒤의 소비자가 이벤트를 잃는다.
- 설정 변경과 저장은 App 계층이 소유한다. UI의 설정 콜백을 GameCommand로 억지로 넣지 않는다. 렌더러는 게임 상태를 변경하지 않는다.

## 5. 실행 수명과 파일 분할

권고 담당 경계:

| 담당 | 파일 | 책임 |
|---|---|---|
| 메인 | `package.json`, `tsconfig*`, `vite.config*`, `index.html`, `src/main.ts`, `src/types.ts` | 설정, 타입 확정, 최상위 연결, 수명 관리 |
| 메인 | `src/platform/input.ts`, `audio.ts`, `storage.ts` | 입력 추상화, Web Audio, 저장과 복구 |
| 전투 구현 | `src/game/engine.ts`, `combat.ts`, `enemies.ts`, `content.ts`, `rng.ts` | 유일한 상태 변경자, 난이도, 조합, 보스, 결과 |
| 렌더링 구현 | `src/render/renderer.ts`, `sprites.ts`, `world.ts`, `effects.ts` | 절차적 아트와 지면, 정렬, 카메라, 이펙트 |
| UI 구현 | `src/ui/ui.ts`, `styles.css`, `icons.ts` | 메뉴, HUD, 성장 카드, 도감, 결과, 접근성 |

큰 함수 하나를 강제로 여러 파일로 분할하지 않아도 된다. **담당 경계와 단일 상태 소유권**이 우선이다. main은 구현자들이 아직 합의하지 않은 API를 추측해 연결하지 않는다.

- `requestAnimationFrame` 루프는 앱당 하나. 고정 1/60초 step을 accumulator로 진행하고 프레임 간 시간은 최대 0.1초, 한 프레임 최대 5 step 정도로 제한한다. 숨김 탭에서 누적된 수십 초를 한 번에 따라잡지 않는다.
- pause/levelup/title/result에서는 시뮬레이션 시간이 진행되지 않는다. RAF는 UI/화면을 유지하되 전투 업데이트를 생략한다.
- blur/visibilitychange에서 실행 중이면 명시적으로 pause하고 눌린 키를 비운다. 복귀 후 자동 전투 재개보다 재개 버튼을 사용한다.
- 재시작은 상태를 새로 만들고 기존 이벤트·이펙트·입력 edge를 비운다. 새로운 RAF나 추가 DOM key listener를 생성하지 않는다.
- 브라우저 이벤트 등록은 create 때, 제거는 dispose 때만 한다. React 등 추가 UI 라이브러리는 이 작업에서 필요하지 않다.
- 저장에는 version, settings, bestStats만 넣는다. 파싱·스키마 오류·localStorage 예외는 기본값으로 복구하고 플레이를 계속한다.
- 실제 게임 상태를 매 프레임 deep-clone하지 않는다. Renderer와 UI에 전달한 상태는 읽기 전용 계약으로 사용한다. UI 수치 업데이트는 최대 10~20Hz, phase 변경은 즉시 반영한다.

## 6. 단계별 콘텐츠 설계

### P0: 첫 100~110분의 구현 목표

**검·활·수호 정령**을 먼저 완성하면 근접 범위·원거리 관통·공전 접촉의 세 가지 플레이가 드러나며 요구된 조합 두 개를 만들 수 있다.

| 무기 | 행동 | 눈에 보이는 차이 |
|---|---|---|
| 검 | 가까운 적 방향 부채꼴 베기 | 큰 크림/금색 호, 준비 뒤 한 번의 넉백 |
| 활 | 가까운 적 방향 직선 화살 | 긴 이동 궤적, 관통/분열 업그레이드 |
| 수호 정령 | 플레이어 주변 공전, 접촉에 주기 피해 | 둥근 보라/금색 정령과 빛의 궤도 |

일반 적은 슬라임(직접 추격), 버섯 정령(접근 뒤 정지·탄 발사), 고블린(주황 선으로 예고한 짧은 돌진) 세 종류를 먼저 만든다. 체력과 색만 다른 세 적으로 세지 않는다.

P0 업그레이드 8종: 힘(피해), 신속(공격 주기), 생명(최대HP와 일부 회복), 장화(이동속도), 자석(경험치 반경), 관통(활 관통 수), 분열(활 1차 적중 시 보조 화살), 연쇄 룬(정령 접촉 시 가까운 두 번째 적으로 전격).

확인할 두 조합은 **활+관통+분열**, **정령+연쇄 룬**이다. 성장 카드에 필요한 무기를 표시하고, 해당 무기를 보유한 경우 카드가 나오는 방식으로 헛선택을 줄인다. 활/정령을 보유하지 않았을 때에는 무기 획득 카드가 먼저 나온다.

보스는 버섯 왕 한 종으로 시작한다. 패턴 A는 바닥의 넓어지는 원과 포자 고리, 패턴 B는 바닥에 순서대로 예고되는 버섯 낙하/폭발 원이다. 둘 모두 예고 시간과 회피 빈 공간이 있어야 한다. 보스 체력바와 등장 알림을 제공한다.

### P1: P0 검증 뒤에만 추가

- 무기 추가: 화염 지팡이(투사체 착탄 폭발), 서리 마법서(목표 지점 둔화 장판), 번개 룬석(가까운 적 사이 순간 연쇄). 기존 무기의 색만 바꾸지 않는다.
- 적 추가: 방패 해골(전방 방어·느린 접근), 박쥐(선회 후 돌진), 숲 주술사(주기 버프 장판). 셋의 행동 구현과 읽을 수 있는 실루엣을 함께 추가한다.
- 업그레이드 추가 8종: 갑옷, 재생, 범위, 다중탄, 공전 정령 수, 냉기, 치명타, 대시 쿨다운. 합계 16종. 각 카드의 실제 수치와 적용 대상을 표시한다.
- 두 번째 보스 돌 골렘: 길쭉한 지면 강타선 3개 + 예고 후 돌진·착지 원. 버섯 왕과 공격 기하를 달리한다.
- 캐릭터 기사(검·HP), 궁수(활·속도), 마법사(화염 지팡이·범위). 특성은 작은 시작 차이로 제한하고 별도 경제/해금 기능을 발명하지 않는다.
- 도감은 무기·적·두 조합을 설명하는 정적 UI로 충분하다.

### P2: 남은 시간과 검증 여유가 있을 때

- 모든 랜덤 호출을 처음부터 seed RNG로 모아 두면 P2 시드 도전은 같은 엔진에 seed 입력 UI만 연결할 수 있다. 시각용 RNG와 전투용 RNG를 분리하여 파티클 수 설정이 적 생성에 영향을 주지 않게 한다.
- 게임패드와 터치는 InputFrame에 연결한다. 방향 벡터·대시·일시정지 외에 별도 전투 코드가 필요하지 않다.
- 게임패드 deadzone, 버튼 edge, 터치 pointer capture와 pointercancel을 포함한다. 미구현 상태에서 지원 버튼이나 설명을 먼저 표시하지 않는다.

## 7. 성장·종료·시연 규칙

- 최대 장착 무기 4칸을 권한다. 신규 무기 카드와 기존 무기 성장 카드를 구분하고, 3개 선택지에는 중복 ID나 이미 최대치인 선택지를 넣지 않는다.
- 효과는 base stats + 업그레이드 레벨에서 다시 계산한다. 공격속도 같은 수치를 매번 곱해 누적 오차와 재시작 오류를 만들지 않는다.
- 여러 레벨을 한 번에 올렸다면 선택을 한 번 끝낼 때마다 다음 레벨 선택을 처리한다. 선택 중 적·타이머·발사체는 모두 정지한다.
- 관통 화살은 hitIds로 재적중을 막는다. 분열은 `generation===0`인 원본 화살에서만 발생한다. 분열탄이 다시 분열하거나 정령의 연쇄 피해가 다시 연쇄를 발생시키지 않는다.
- 정상 duration은 600초, demo duration은 180초다. demo는 같은 피해/성장/보스 함수를 쓰되 director 일정과 경험치 보상을 압축한 **명시적인 3분 시연 모드**다. 단순 승리 버튼이나 녹화 애니메이션으로 대체하지 않는다.
- 권고 종료 규칙: 마지막 보스는 종료 30~45초 전에 등장한다. 승리는 `elapsed>=duration && finalBossDefeated`. 시간이 0이 되어도 보스가 살아 있으면 HUD는 “최종 보스를 처치하세요”로 바뀌고 전투를 계속한다. HP 0은 즉시 패배다. 사용자가 이해할 수 있도록 시작 화면에 이 규칙을 한 문장으로 명시한다.
- P1 첫 보스는 정상 중반(약 270초), demo 중반(약 70초)에 추가한다. P0 보스를 P1 추가 과정에서 조용히 삭제하지 않는다.
- 기록은 normal/demo/challenge를 구분한다. 시연의 빠른 성장 기록이 정상 모드 최고 기록을 덮지 않는다.
- 시연 경로는 기사 선택→이동/대시→레벨업 활 획득→관통/분열 또는 정령/연쇄 확인→보스 예고 회피→결과다. 필요한 카드가 끝없이 안 나오는 것을 피하려면 demo 선택지의 순서만 고정하되, 모든 전투와 피해는 실제 기능으로 실행한다.

## 8. 성능 전략과 확인할 숫자

- 캐릭터/적의 복잡한 경로를 개체마다 매 프레임 그리지 않는다. 절차적 형태를 작은 offscreen canvas/atlas에 미리 그린 후 drawImage한다. 애니메이션은 4~6 자세 + bob/기울기/무기 overlay로 만든다.
- OffscreenCanvas가 필수인 구조는 피한다. 일반 canvas element를 메모리 캔버스로 써도 된다. 픽셀 아트용 계단이 생기지 않게 필요한 해상도로 생성한다.
- 지면은 512px 정도 chunk로 캐시하고, 나무·돌·건물도 캐시한다. 시야 밖 렌더링을 하지 않는다. DPR은 초기 최대 1.5~2로 제한하고 실제 화면 선명도를 확인한다.
- 적-투사체 충돌은 적 수가 늘면 64~96 world unit 공간 해시를 사용한다. 적끼리의 완전한 O(n²) 밀어내기는 피하고 가까운 셀만 검사한다.
- 시작 성능 예산: 적 220, 투사체 260, 파티클 450, 피해 숫자 50 정도. 이는 **측정 전 작업 예산**이며 달성 성능이 아니다. 개체 제한은 큐/병합/오래된 파티클 제거로 처리하고 정상 적 처치·보스 피해를 임의 생략하지 않는다.
- 경험치 조각은 가까운 작은 조각들을 합치거나 일정 거리 안에서 자석으로 끌어와 무한 누적을 막는다. 보스·위험 예고·플레이어는 품질 자동 하향 대상에서 제외한다.
- 대표 부하 장면에서 해상도, 브라우저/환경, 적·발사체·파티클 수, 측정 시간, 평균 및 p95 frame time을 기록한다. 60fps를 목표로 하되 측정 전에는 통과라 쓰지 않는다.

## 9. 실행 가능한 통합 순서

1. 대시보드 URL/갱신 확인 후 메인이 공용 타입과 최소 앱을 만든다.
2. 전투·렌더·UI 세 담당만 병렬 구현한다. 최초 장면에서 기사+슬라임+버섯, 땅+성벽/나무+높이가 다른 소품, 이동·공격·피격·그림자·가림·실제 크기 HUD를 확인한다.
3. 한 무기로 시작→전투→레벨업→패배→재시작 흐름을 통합한 뒤 P0 세 무기·세 적·8업그레이드·보스를 붙인다.
4. 1280×720 및 1920×1080 화면과 키보드 조작, 일시정지, 손상 저장 복구를 확인한다. 정상 10분 1판과 demo 3분을 실제 입력으로 검증한다.
5. P0 결과가 안정적일 때만 P1을 추가한다. P2는 P1과 핵심 검증을 밀어내지 않는다.
6. 마지막 약 40분은 새 기능을 멈추고 승리/패배, 3회 재시작, 조합 2개, 보스 2패턴, 성능, 프로덕션 빌드·문서·캡처를 마감한다.

현재 검증: 원문 요구사항과 빈 저장소 상태 읽기만 완료. 렌더링/기능/브라우저/성능은 모두 구현 후 검증해야 한다. 변경 파일은 이 보고서 한 개뿐이다.
