# Q00 — P0 검증 설계

기준 문서: `PROJECT_REQUEST.md`, `SPEC.md`, `DECISIONS.md`  
검증 대상: 통합이 끝나고 변경이 동결된 단일 빌드(커밋 SHA, 브라우저 버전, 실행 URL, 검증 시각 기록)  
우선 원칙: 개발용 시드·진입 기능은 재현과 단위 검증에만 쓴다. 최종 P0 판정은 시작 화면에서 일반 키보드 입력으로 진행한 정상 플레이 근거를 요구한다.

## 판정 규칙

- **통과**: 아래 매트릭스의 기대 결과와 증거가 모두 있다. 작성자의 완료 보고만으로 통과시키지 않는다.
- **실패**: 재현 절차, 실제 결과, 기대 결과, 심각도(P0 진행 차단 / P1 중요 / P2 경미), 캡처 또는 로그를 남긴다.
- **미검증**: 도구·시간·구현 부재 때문에 실행하지 못한 항목이다. 통과로 바꾸지 않는다.
- 최종 플레이 중 콘솔 `error`, 페이지 예외, 처리되지 않은 Promise 거부가 하나라도 있으면 해당 경로는 실패다. 의도된 네트워크 404도 원인 확인 전에는 실패로 둔다.
- 최종 검증 중 코드가 바뀌면 영향받는 항목을 다시 실행한다. 다른 에이전트가 수정 중인 빌드는 최종 판정에 쓰지 않는다.

## 효율적인 실행 순서

1. **정적 게이트(약 5분)**: 설치 재현, 타입 검사, 프로덕션 빌드, 단위/통합 검사. 피해 계산, 성장 3선택, 종료 조건, 저장 파싱과 기본값 복구를 자동 검사한다.
2. **정상 승리 한 판(실시간 약 11분)**: 1920×1080 새 브라우저 컨텍스트에서 첫 화면부터 시작한다. WASD/방향키, 대시 키, Esc와 화면에 보이는 성장 선택만 사용한다. 10분 생존, 보스, 승리 결과까지 진행한다. 이 한 판에 조작 안내, HUD, 자동 공격, 세 적/세 무기/8 업그레이드의 노출, 난이도 상승, 일시정지, 음소거, 화면 흔들림 감소, 두 조합 중 하나, 보스 예고/두 패턴, 고부하 계측을 함께 확인한다.
3. **패배 경로 + 재시작 3회(약 6분)**: 결과 화면에서 재시작을 3회 연속 수행한다. 각 새 판에서 20초간 이동·대시하고 타이머 감소량, 초당 적 생성/공격 또는 관찰 가능한 동작 수가 이전 판과 비정상적으로 배가되지 않는지 확인한다. 마지막 판은 적에게 접근해 의도적으로 체력을 소진하고 패배 결과를 확인한다. 패배를 만들기 위한 체력 직접 변경은 금지한다.
4. **해상도·저장·복구(약 6분)**: 1280×720에서 시작/플레이/성장/일시정지/결과의 주요 패널 경계를 확인한다. 음소거와 흔들림 감소를 저장한 뒤 새로고침 및 새 탭에서 유지되는지 확인한다. 이후 별도 컨텍스트에서 저장 없음, 잘못된 JSON/잘못된 타입 저장을 각각 주입하고 정상 시작과 기본값 복구를 확인한다. 손상 저장 주입은 복구 시험에만 허용한다.
5. **두 번째 조합·3분 시연(약 4분)**: 정상 입력으로 제공된 3분 시연 경로를 실행하고 두 번째 조합의 실제 효과 차이를 확인한다. 시연 경로가 개발용 빠른 진입이면 P0 기능 시연 증거로만 인정하고, 정상 승리 한 판의 대체 증거로 쓰지 않는다.
6. **증거 정리(약 5분)**: 시작, 성장 선택, 보스전, 승리, 패배, 720p/1080p, 고부하 화면과 계측 결과를 묶고 매트릭스를 판정한다.

## 정상 플레이 자동화 경계

최종 정상 플레이 자동화는 브라우저의 실제 사용자 입력 인터페이스만 사용한다.

- 허용: 화면에 보이는 버튼 클릭, `keyboard.down/up/press`로 WASD·방향키·대시·Esc·숫자/Enter 입력, 실제 시간 경과 대기, 화면/접근성 트리/캔버스 캡처, 콘솔·페이지 예외 수집, 프레임 간격 계측처럼 결과를 바꾸지 않는 관찰.
- 금지: `window` 내부 게임 객체 호출, HP/XP/타이머/적 수 직접 변경, DOM에서 숨은 개발 버튼 호출, 네트워크 응답 변조, 이벤트 디스패치로 게임 입력 계층 우회, 시간을 가속해 10분 정상 판 대체, 승리 상태 직접 설정.
- 개발 경로 허용 범위: 고정 시드 재현, 특정 성장/보스 진입, 저장 손상 주입, 단위 테스트용 가상 시간. 결과에는 항상 **개발 경로**로 표시하며 Q-P0-09 정상 승리와 Q-P0-10 정상 패배의 근거로 사용하지 않는다.
- 공용 계약의 `window.__LRG__.getState()`와 `getDiagnostics()`는 구조화 복제된 읽기 전용 스냅샷이므로 이동 판단과 계측에 사용할 수 있다. 이 API에 상태 변경 함수가 없어야 하며 `version`을 기록한다. 모든 핵심 상태는 화면 관찰과 교차 확인한다.

## 실제 플레이 입력 계획

자동 플레이가 필요하면 화면 캡처와 읽기 전용 `getState()` 스냅샷으로 다음 입력만 선택하는 단순한 플레이어를 사용한다. 플레이어와 가까운 적/위험의 좌표는 회피 방향을 정하는 데 쓸 수 있지만 결과 상태는 바꾸지 않는다. 200~500ms 단위로 한두 방향 키를 Playwright `keyboard`로 누르고, 위험 접근 시 대시 키를 누르며, 성장 화면이 실제로 나타났을 때 보이는 세 선택지 중 하나를 클릭하거나 숫자 키로 고른다. 조합 목표는 화면에 표시된 선택 이름을 우선순위로 정한다. 자동 플레이가 생존에 실패하면 사람이 동일한 일반 입력으로 수행하고, 개발 치트로 보정하지 않는다.

한 판 증거에는 입력 이벤트 요약(키, 상대 시각), 매분 화면, 성장 선택 내역, 일시정지 구간, 보스 패턴, 결과 화면을 남긴다. 10분은 게임 타이머와 벽시계를 함께 기록한다. 두 값 차이가 일시정지 시간을 제외하고 과도하면 타이머 결함으로 조사한다.

## 고부하 측정 설계

- 측정 대상은 정상 승리 판에서 화면상 적/투사체/효과가 가장 많은 연속 60초다. 개발용 대량 생성 장면은 최적화 재현용 보조 자료로만 둔다.
- 고정 조건: 프로덕션 미리보기, 1920×1080, 브라우저 확대 100%, 전원 상태와 하드웨어 가속 여부, 브라우저/OS, CPU/GPU를 기록한다. DevTools를 열어 생기는 왜곡을 피하고 페이지 안 읽기 전용 `requestAnimationFrame` 샘플 또는 Playwright 평가로 프레임 간격만 수집한다.
- 함께 기록: 구간 시각, `getDiagnostics()`의 개체·입력 등록 수, 화면상 적·투사체·효과 수, 평균 FPS, 중앙값, 1% low에 해당하는 프레임 지표, 50ms 이상 긴 프레임 수, 최대 프레임 시간. 진단값은 화면과 교차 확인하고 평균만으로 통과시키지 않는다.
- 60fps는 목표다. 평균 미달 또는 반복적인 긴 프레임으로 조작이 끊기면 결함을 등록한다. 요구 문서가 하한을 확정하지 않았으므로 수치를 숨기거나 임의 하한으로 통과 처리하지 않는다.
